# 线上微服务故障根因定位 Agent（RCA Agent）产品需求文档（PRD）

- 版本：v0.1（评审稿）
- 编写日期：2026-08-03
- 状态：待产品评审；评审通过后进入 MVP 开发
- 依据：已完成业界 RCA 架构调研（传统工具 / 经典方法 / LLM Agentic RCA / 评测与风险，见 `docs/research/`），本 PRD 基于调研结论 + 用户确认的三项硬约束编写

---

## 1. 背景与问题定义

### 1.1 现状痛点

团队为微服务架构，线上故障发生后完全依赖人工排查根因：

- **定位链路长、耗时高**：一次故障的诊断阶段（MTTR 中的"定位"部分）约 1～4 小时，复杂跨服务故障可达半天。故障期间业务持续受影响。
- **排查手段割裂**：日志、监控指标、traceId 三套数据分散在不同系统，人工需来回切换、手工拼凑；**只有 traceId、没有完整链路调用树，每次靠人肉从多个服务的日志按 traceId 手工重拼调用顺序**，易漏看、看错。
- **强依赖个人经验**：定位效率取决于当班人是否"见过类似的坑"，经验无法复用，新同学值班效率断崖下降。
- **无变更记录可用**：团队无系统化的部署/配置变更登记，无法用"上线导致故障"这条捷径缩小范围，只能靠数据信号反推。
- **故障复盘靠事后人写**：报告格式不统一、证据留存不全，审计与知识沉淀质量差。

### 1.2 为什么现在做

- **技术时机成熟**：业界"确定性工作流 + LLM 判断"的混合架构（微软 RCACopilot、字节 Flow-of-Action、阿里 RCAgent 等）已证明能把"调查草稿"自动化。
- **可用数据已具备**：线上日志、机器级监控指标、traceId 三类信号已具备，只差一个把它们组织起来的执行层。
- **投入产出比高**：MVP 定位是"AI 调查草稿 + 人复核"，目标是**把诊断 MTTR 从小时级降到分钟级、产出高质量调查线索**，而非全自动确诊，风险可控。

### 1.3 成功定义（一句话）

**当一条新告警/事件进来后，RCA Agent 在 15 分钟内产出一份带证据链、按置信度排序的候选根因报告，值班人员 30 分钟内完成复核并形成可执行的处置/修复方向，整体诊断 MTTR 从平均 2 小时降至 45 分钟以内。**

## 2. 目标与非目标

### 2.1 MVP 目标（可量化）

| 指标 | 现状 | MVP 目标（验收口径） |
|---|---|---|
| 诊断阶段 MTTR | 平均 120 分钟 | **≤ 45 分钟**（Agent 草稿 ≤ 15 min + 人复核 ≤ 30 min） |
| 根因命中 | 依赖个人经验 | **Top-3 命中率 ≥ 60%**（在自建历史故障回归集上） |
| 报告质量 | 格式不一、无证据链 | 100% 报告含证据链与置信度、证据引用完整率 ≥ 90% |
| 可审计性 | 无 | 每次调查全轨迹留痕、可回溯 |

> 说明：行业最佳在公开基准上 Top-1 命中率也只有约 42%（RCAEval 上 GALA 42.22%），因此 Top-1 不作为 MVP 验收硬门槛，Top-3 是现实目标。MVP 本质价值是"把人工从 0→1 的排查变成 1→2 的复核"。

### 2.2 非目标（明确不做）

- **不做自动修复/自愈**：Agent 全部只读；写操作（重启/回滚/扩容）不在本期范围，修复建议仅停留在报告文本，执行必须人工完成。
- **不做变更关联**：无部署/配置变更记录可依，MVP 不把变更数据作为主信号（作为后续 Phase 外部可选补充）。
- **不做完整链路存储/调用树建设**：不新增链路追踪系统，只在现有日志上按 traceId 重建调用序列，重建质量依赖日志埋点完整性。
- **不做全部故障类型覆盖**：MVP 聚焦高频场景，不承诺覆盖所有微服务问题。
- **不做多租户/平台级接入**：先接通一个代表性业务域 + 一个日志集群 + 一套监控，验证后横向扩展。
- **不做 LLM 直出终审结论**：LLM 输出永远是"候选假设 + 证据"，终审判定由规则打分 + 人工确认完成。

### 2.3 成熟度定位

参照阶梯：L0 告警+人工 → L1 规则定位 → L2 LLM 辅助 → L3 全自动 Agent → L4 自愈。
**MVP 定位在 L2→L3 之间**：LLM 辅助、可审计、人在环上（HITL）把关，不追求全自动。

## 3. 用户故事与角色

### 3.1 角色

| 角色 | 职责 | 使用诉求 |
|---|---|---|
| **On-call 值班人员（一线）** | 第一时间响应告警，判断影响范围 | 快速拿到"发生了什么、哪里最先开始、最可能是谁"的草稿，别让我逐条翻日志 |
| **SRE（专家复核）** | 对 Agent 结论做专业复核 | 能看到完整证据链与推理过程，能一键采信/纠偏/驳回，把结论固化进知识库 |
| **研发（故障 Owner）** | 认领具体故障、负责修复 | 拿到带证据的时间线 + 修复建议，报告能导出分享 |

### 3.2 核心用户故事（MVP 验收用）

- **US-1（值班接线）**：收到告警时系统自动触发调查并在 15 分钟内给出候选根因报告，先处理影响、再复核细节。
- **US-2（证据复核）**：每个根因论断能一键跳转到原始证据（日志原文/指标曲线/重建的调用序列），验证它没有胡说。
- **US-3（链路重建）**：给一条 traceId，系统自动聚合所有相关服务日志并画出"Service A→B→C 每跳耗时/错误"的时序图，不必手工重拼。
- **US-4（基线对比）**：看到"故障时段 vs 正常时段"的指标与日志模式对比，判断突变还是长期累积。
- **US-5（反馈闭环）**：纠正 Agent 结论后，这次纠偏被记录用于后续改进，系统越用越准。
- **US-6（审计追溯）**：每次调查有完整审计轨迹，复盘与追责有据可查。

## 4. 产品功能需求

> 编号规则：RCA-xxx。优先级：P0 = MVP 必须；P1 = MVP 应做（可延后到 Phase 2）；P2 = 后续增强。

### 4.1 故障事件输入与触发方式（P0）
- **RCA-001 告警自动触发**：对接告警系统（Prometheus Alertmanager / 自研平台）webhook，收到告警即生成 `IncidentEvent` 并排队进入调查队列。
- **RCA-002 手动触发/补录**：支持页面用"traceId / 服务名 + 时间窗口 / 自由文本"手动发起调查（覆盖告警缺失、非告警类故障）。
- **RCA-003 事件归一化与去重**：时间窗口内重复告警自动合并；支持事件升级（多个关联告警归并为一个事件）。
- **RCA-004 事件解析**：从告警文本/标签解析故障服务/实体、指标名、告警级别、时间窗口、可能的 traceId；解析失败降级为"仅时间窗口 + 服务名"。

### 4.2 自动调查流程（P0）
- **RCA-010 全流程自动编排**：一次调查 = 一个 LangGraph 状态机工作流（第 6 章），7 步串联，中间态可中断/可恢复/可人工介入。
- **RCA-011 分步超时与预算控制**：总时间预算（如 10 分钟）+ 总 token 预算（如 20 万/事件），超预算自动收敛到当前最佳结果。
- **RCA-012 失败降级**：任一步失败不中断整体；失败节点返回占位证据 + 错误标记，报告如实标注"该信号缺失/失败"。
- **RCA-013 人工介入点（HITL）**：调查前可补充输入（追加 traceId/时间窗）；默认"自动跑完 + 可中断查看中间态"，不强制每步审批。
- **RCA-014 并发与资源限制**：单实例并发上限（如 3），超限排队；告警风暴时按优先级处理。

### 4.3 证据链（P0）
- **RCA-020 统一证据模型**：所有调查产物以 `Evidence` 对象管理，含唯一 `evidence_id`、类型（log/metric/trace/scenario）、来源、时间、摘要、原文快照。
- **RCA-021 强制证据引用**：报告每个论断必须引用 ≥1 个 `evidence_id`；无证据支撑的表述只能出现在"推测/待验证"区并明确标注。
- **RCA-022 确定性校验层**：报告生成前做规则校验——时间先验（原因时间 ≤ 症状时间）、跨信号一致性（日志异常与指标异常时间对齐）、链路传播方向一致性；不通过的在报告中降级标注。
- **RCA-023 证据可回跳**：每条证据可一键跳转到原始数据。

### 4.4 根因报告输出（P0）
- **RCA-030 结构化根因报告**：输出 `RCAReport`：根因候选（Top-3 带置信度）、证据链、时间线、修复建议、审计轨迹。
- **RCA-031 多根因候选排序**：不确定时输出 Top-3 候选而非单一结论，每个候选附"支持证据 + 反驳证据 + 置信度"。
- **RCA-032 置信度分档**：≥0.8 高置信、0.5~0.8 中等、<0.5 低置信/需人工；低置信报告必须引导人工介入。
- **RCA-033 快速人工反馈入口**：报告页提供"采信/纠偏/驳回 + 原因"三键闭环。

### 4.5 报告查看/导出（P0/P1）
- **RCA-040 报告 Web 页面**（P0）：事件列表 + 报告详情页，含时间线、链路图、证据 tab。
- **RCA-041 报告导出**（P1）：导出 Markdown / PDF。
- **RCA-042 调查中间态查看**（P1）：查看"调查进行到哪一步、已采集哪些证据"，用于 Agent 卡住时人工接管。

### 4.6 人工反馈闭环（P1）
- **RCA-050 纠偏数据落库**：人工采信/纠偏/驳回记录入库，作为评估与后续优化种子数据。
- **RCA-051 知识库沉淀**：人工确认的根因案例进入"历史故障库"，供 RAG 检索（Phase 2）。

### 4.7 审计（P0）
- **RCA-060 全轨迹审计**：记录事件、每步执行记录（工具调用、查询语句、命中数）、LLM 输入/输出摘要、人工操作；不可变、可追溯、保留 ≥ 90 天。
- **RCA-061 查询留痕**：所有对日志/指标系统的查询可还原（含 DSL 与时间窗）。

### 4.8 优先级汇总
- **P0（MVP 核心）**：RCA-001~004、010~014、020~023、030~033、040、060~061。
- **P1（可顺延）**：RCA-041、042、050、051。
- **P2（后续）**：多租户、更多故障类型、自动修复建议执行、相似案例推荐、历史故障 RAG 增强。

## 5. 数据信号接入需求

> 硬约束：只依赖三类信号——线上日志、机器监控指标、traceId（无完整链路存储）。

### 5.1 日志接入（P0）
- **数据源**：现有线上日志系统（查询方言待确认：ES DSL / LogQL / KQL 之一；本期只接一种，后续抽象统一查询接口）。
- **接入方式**：通过现有日志查询 API 按索引/服务 + 时间窗口检索；只做查询接入，不做采集建设。
- **字段约定（日志行须能解析出；缺项则降低链路重建置信度）**：

| 字段 | 说明 | 是否必需 |
|---|---|---|
| `@timestamp` | 日志时间（毫秒级） | 必需 |
| `service` | 服务名 | 必需 |
| `host`/`instance` | 机器标识 | 必需（用于与指标对齐） |
| `traceId` | 关联主键 | 建议必需（链路重建依赖） |
| `level` | info/warn/error 等 | 建议 |
| `message` | 日志正文 | 必需 |
| `rpc_direction` | 调用方向（out=发出调用 / in=接收请求） | 建议（强链路重建用） |
| `rpc_target`/`method` | 对端服务/接口名 | 建议 |
| `exception` | 异常堆栈 | 建议 |

- **查询模式（NL→DSL）**：LLM 生成查询意图 → 确定性解析器/DSL 生成器产出 DSL → 执行前校验（时间窗必带、索引白名单、查询大小上限）→ 执行 → 结果裁剪。给 LLM 提供字段 schema + 5~10 条 few-shot 示例。
- **降采样与聚合**：单次查询限制返回条数（如 1000 条）；超限先做模板聚类/聚合再取代表样本。

### 5.2 指标接入（P0）
- **数据源**：机器级监控（CPU/内存/磁盘/网络 + 业务指标，Prometheus 语义）。
- **接入方式**：指标库查询 API（PromQL 语义）。**确定性优先**：查询后先做异常检测再决定是否喂 LLM。
- **确定性异常检测（前置）**：对指标序列做 MAD / 3σ 突变检测与趋势检测，输出"哪个指标、什么形态（突增/突降/持续走高/锯齿）、什么时间点开始异常"的**结构化摘要**喂 LLM，而非原始时间序列。
- **text2PromQL（按需工具）**：LLM 需要额外指标时用 NL 生成 PromQL，由**执行校验层**（语法校验 + 指标名白名单 + 时间窗约束）把关后执行。
- **指标-机器对齐**：通过日志中的 `host/instance` 把日志异常与机器指标异常关联到同一实体。

### 5.3 traceId 重建调用链（P0，本项目关键路径）

> 约束：只有 traceId、无完整链路存储，因此**链路重建 = 以 traceId 为主键，从日志系统聚合该 traceId 在所有服务上的全部日志，再重建调用序列**。这是本项目最核心、也最需要产品上明确认知边界的能力。

**流程**：
1. **聚合**：按 `traceId == {id}` + 时间窗（trace 开始时间 ± 宽裕窗），跨全部服务索引检索该 traceId 的全部日志行。
2. **归一**：按 `service` 分组，每行提取 `@timestamp`、`rpc_direction`、`rpc_target`、错误标记。
3. **重建**：按时间序，用 `rpc_direction=out` 与下游 `rpc_direction=in` 匹配（out 的服务 → in 的服务形成一跳），拼接出 `Service A → B → C …` 序列；每跳计算**耗时**（out 时间 → 下一 in/out 时间差）与**是否含错误**（error 日志 / 异常堆栈 / 超时标记）。
4. **定位慢/错节点**：计算每跳耗时分布，标记异常跳（P95 显著高于全局、或携带 error）。
5. **基线对比**：同一服务、同类型 trace（同入口接口）在正常时段的 P50/P95 耗时作为基线，判断"该跳慢"还是"整体都慢"。

**认知边界（产品中必须诚实暴露）**：
- 重建质量取决于日志埋点完整性（`rpc_direction` 缺失时退化为"按时间聚合，无法精确判定调用方向"，报告标注为"弱重建"）；
- traceId 为空/未透传的调用无法进入重建，报告标注覆盖范围；
- 无法拿到 SQL/Redis 等中间件细粒度 span 时，只能依赖日志中的 RPC 方向字段推断。

**调用方约定（Phase 0 需与研发确认）**：后续可推动在 RPC 框架层补齐 `rpc_direction`/`rpc_target` 埋点，作为"数据质量"配套项目，不阻塞 MVP。

## 6. RCA Agent 工作流设计

> 架构原则：**确定性优先、LLM 次之**。证据采集与校验交给工具与规则，LLM 只负责推理、查询意图生成与报告润色。整体为 LangGraph 状态机（可 checkpoint、可恢复、可人工介入）。

### 6.1 总览

```
IncidentEvent 进入
   │
   ▼
[1 事件解析]   规则 + LLM 抽取实体/时间窗/类型      → incident_context
   ▼
[2 场景认知]   规则分类 + LLM 判定故障类型          → scenario
   ▼
[3 链路重建]   工具聚合 traceId 日志 → 确定性重建    → trace_graph
   ▼
[4 日志分析]   工具聚类去噪 → LLM 精读异常簇        → log_evidence
   ▼
[5 指标验证]   确定性 MAD/3σ 异常 → text2PromQL 按需 → metric_evidence
   ▼
[6 假设生成/打分] 规则打分 + LLM 排序 → 候选根因      → hypotheses
   ▼
[7 报告生成]    校验层 → 格式化（不调 LLM 二次推理）  → RCAReport
```

### 6.2 分步细节（输入 / 输出 / 工具 / LLM 职责 / 规则职责）

| 步骤 | 输入 | 输出 | 工具 | LLM 职责 | 规则/确定性职责 |
|---|---|---|---|---|---|
| **1 事件解析** | 原始告警/手动输入 | `incident_context` | 告警 webhook、事件解析器 | 从自由文本抽取实体/接口名；给置信度 | 时间窗校验、告警去重合并、字段校验 |
| **2 场景认知** | `incident_context` | `scenario`（延迟突增/错误率飙升/资源饱和/可用性下降/慢 SQL） | — | 基于摘要做场景分类（枚举约束） | 预置候选场景列表约束 LLM 枚举；schema 校验 |
| **3 链路重建** | traceId + 时间窗 | `trace_graph`（每跳耗时/错误、置信度标签） | 日志检索、trace 聚合器 | 不参与核心重建（纯确定性）；弱重建时辅助"猜测调用关系并标注低置信" | 聚合、时间序拼接、跳耗时计算、基线对比 |
| **4 日志分析** | 故障窗日志 + trace_graph | `log_evidence`（异常模板簇、代表原文、错误统计） | 日志检索、日志聚类器（Drain） | 对**聚类后的异常簇摘要**精读，提取"发生了什么、哪个组件、什么异常类型" | 预过滤噪音（heartbeat/健康检查/已知噪音模板）、模板聚类（token 可降 ~85%）、采样限制 |
| **5 指标验证** | 故障窗指标 + 基线窗指标 | `metric_evidence`（异常指标摘要、形态、时间点） | 指标查询、MAD/3σ 检测器、text2PromQL | 决定"还需查哪些指标"并生成 PromQL | 异常检测、形态识别、时间点定位、指标名白名单、PromQL 校验执行 |
| **6 假设生成/打分** | 全部 evidence + scenario | `hypotheses`（Top-3 + 置信度 + 支持/反驳证据） | 可选 RAG 历史案例（Phase 2） | 基于证据摘要生成候选根因与推理链（不读原始大数据） | 证据基础分、时间先验过滤、跨信号一致性打分、schema 校验 + 确定性兜底 |
| **7 报告生成** | `hypotheses` + 全部 evidence | `RCAReport` | 校验层、格式化器 | **不调 LLM 二次推理**，仅拼装与措辞（或纯格式化） | 强制证据引用校验、时间/一致性校验、模板组装、审计写入 |

### 6.3 关键设计决策

1. **混合架构而非纯 ReAct 自由发挥**：LLM 不拥有"想查就查"的无界自由；每步查询范围、时间窗、返回上限都由规则约束（参考 RCACopilot / Flow-of-Action / RCAgent）。
2. **子 Agent 委派与证据压制**：日志分析、指标验证可各自运行在一个**有界上下文的最小 ReAct 循环**（max_iters≈4）中，只把**压制成一条 Evidence** 的结论写回共享状态——互不污染、单点失败不拖垮全局。
3. **LLM 输入最小化**：所有喂给 LLM 的内容都先经确定性缩减（聚类摘要、指标异常摘要、Trace 统计），LLM 原则上不读原始日志大海——控制 token 成本与幻觉的最重要手段。
4. **中间态可见 + 可人工接管**：把 `step` 与已收集证据持久化（LangGraph checkpoint + 存储），支持中断查看、修改输入后恢复。

### 6.4 LLM 调用规格（DeepSeek 约束下）

- **模型**：`deepseek-chat` 用于抽取/分类/查询意图（稳定、便宜、格式化好）；`deepseek-reasoner` 仅用于"假设生成/打分"这类强推理步骤（可选开关）。
- **temperature**：结构化产出步骤 = 0；推理步骤 ≤ 0.3。
- **结构化输出（硬约束 3）**：DeepSeek OpenAI 兼容 API **不支持 Structured Output / `response_format=json_schema`**，统一走 **"提示词强约束 JSON 输出 → `json.loads` 解析 → `jsonschema` 校验 → 校验失败重试（≤3 次，逐步追加"上次解析错误"反馈）→ 仍失败则确定性兜底（取规则评分最高候选/降级输出）"**。封装为统一 `LLM.ask_json()`，所有步骤共用。
- **上下文管理**：每步只取小窗口；提示词显式声明"忽略与本步无关的证据"（缓解 lost-in-the-middle）；超长日志强制先聚类再进上下文。

## 7. 架构设计与技术选型

### 7.1 分层架构（文字版）

```
┌─────────────────────────────────────────────────────────────┐
│  表现层   报告 Web 页 / 导出 / 人工反馈入口（FastAPI + 前端）     │
├─────────────────────────────────────────────────────────────┤
│  报告层   RCAReport 组装 · schema 校验 · 强制证据引用 · 审计写入  │
├─────────────────────────────────────────────────────────────┤
│  Agent 编排层  LangGraph 状态机 · checkpoint · HITL · 子 Agent  │
│               委派 · 时间/token 预算 · 失败降级                   │
├─────────────────────────────────────────────────────────────┤
│  关联分析层  假设生成/打分 · 时间先验 · 跨信号一致性 · 历史案例 RAG  │
├─────────────────────────────────────────────────────────────┤
│  信号提取层  日志聚类/去噪 · MAD/3σ 异常检测 · traceId 链路重建     │
│              确定性优先，LLM 只做意图/推理                         │
├─────────────────────────────────────────────────────────────┤
│  数据接入层  ES(日志) 查询适配 · Prometheus 查询适配 · NL→DSL      │
│              解析器 + 执行校验层（时间窗/白名单/上限）              │
├─────────────────────────────────────────────────────────────┤
│  数据源   线上日志系统 · 机器监控指标 · (traceId 经日志聚合重建)     │
└─────────────────────────────────────────────────────────────┘

横向公共件：
  · 存储：Postgres（事件/报告/证据/反馈/审计）+ Redis（队列、限流）
  · LLM：DeepSeek（OpenAI 兼容 API，经 ask_json shim 统一接入）
  · 结构化 shim：提示词约束 + jsonschema 校验 + 重试 + 确定性兜底
  · 认证/权限：值班/复核/管理员三级
```

### 7.2 技术选型清单

| 层 | 选型 | 理由/备注 |
|---|---|---|
| 编排框架 | **LangGraph** | 状态机 + checkpoint + HITL + token 开销低 + 生产背书厚；DeepSeek 经 OpenAI 兼容接口接入（`ChatOpenAI(model="deepseek-chat", base_url=...)`）。备选：自研 ReAct loop。 |
| 主语言/运行时 | Python 3.11+，FastAPI | LLM/Agent 生态最成熟；Web API 承载报告与人工操作。 |
| LLM | DeepSeek `deepseek-chat`（主力）+ `deepseek-reasoner`（可选强推理） | 硬约束 3；统一 `ask_json` shim。 |
| 日志检索 | ES DSL 适配器（与现有日志系统对接，方言待确认） | 只做查询接入，不做采集建设。 |
| 指标检索 | PromQL 适配器 + MAD/3σ 检测器 | 确定性异常先行。 |
| 日志聚类 | Drain（模板聚类）或轻量聚类算法 | 去噪、压缩 token ~85%。 |
| 状态/存储 | Postgres（业务数据）+ Redis（队列/限流/缓存） | 事件、证据、报告、审计持久化。 |
| 前端 | React/Vue + 图表库（链路图/时间线） | 报告查看、反馈、中间态查看。 |
| 评估 | RCAEval / AIOpsLab 公开基准 + 自建历史故障回归集 | 见第 9 章。 |
| 可观测 | 标准日志/指标埋点，Agent 自身行为可观测 | 审计 + 调参用。 |

### 7.3 成本与性能设计要点

- **token 预算**：单事件默认 ≤ 20 万 token（DeepSeek 约几元级成本），超预算走确定性收敛。
- **查询预算**：单事件对日志/指标的查询次数上限（如 ≤ 20 次），防止 LLM 在低价值查询上打转。
- **并发上限**：单实例 3 并发，超限排队；告警风暴按优先级处理。

## 9. 评测与验收标准

### 9.1 评测指标

| 指标 | 定义 | 目标值（MVP 验收） |
|---|---|---|
| **Top-1 / Top-3 命中率** | 报告候选是否覆盖人工最终确认根因 | Top-3 ≥ 60%（Top-1 作观察项） |
| **MRR** | 命中候选的排序倒数均值 | ≥ 0.55 |
| **定位耗时** | 事件进入 → 报告产出时间 | 中位数 ≤ 15 min |
| **幻觉率** | 无证据支撑/证据与论断不符的比例 | ≤ 10%（抽样人工核验） |
| **证据引用完整率** | 论断均有 `evidence_id` 且有效 | ≥ 90% |
| **token 成本/事件** | 单事件 LLM 用量 | 中位数 ≤ 20 万 token |
| **人工复核通过率** | 人工采信/部分采信占比 | ≥ 60% |

### 9.2 评测集建设

- **自有历史故障回归集（主）**：从过往故障复盘/告警历史挑选 30~50 条已有人工确认根因的事件（覆盖 4 类场景、含少量多根因复合），做成 `(IncidentEvent, 期望根因, 期望证据)` 标注集。这是 MVP 验收的权威集。
- **公开基准（辅）**：接入 RCAEval / AIOpsLab 任务做横向参照，受数据信号差异限制仅作参考。
- **评测运行方式**：离线回放（mock 数据源响应）+ 在线灰度（影子模式观察真实事件，报告不对外）。每轮迭代在回归集上全量回归，防止改进 A 破坏 B。

### 9.3 验收门槛（MVP 出口条件）

1. P0 需求全部交付；
2. 回归集 Top-3 ≥ 60%、证据引用完整率 ≥ 90%、幻觉率 ≤ 10%；
3. 真实灰度 ≥ 2 周，≥ 20 起真实事件，人工复核通过率 ≥ 60%；
4. 审计留痕完整、无写操作路径可达；
5. 单事件成本与耗时达标。

## 10. 里程碑与迭代计划

| 阶段 | 交付物 | 验收口径 |
|---|---|---|
| **Phase 0：数据打通（约 2 周）** | 日志/指标查询适配器 + 执行校验层；事件接收与归一化；traceId 日志聚合工具（命令行原型即可） | 能对给定 traceId 拉回多服务日志并画出粗糙调用序列；DSL 校验能拦截非法查询 |
| **Phase 1：确定性 + 基础 Agent（约 3~4 周）** | LangGraph 7 步工作流 v1；日志聚类去噪、MAD/3σ 检测、链路重建确定性化；`ask_json` shim；报告页 v1 + 审计 | 端到端对一条真实告警产出带证据链与候选排序的报告；回归集 Top-3 ≥ 40% |

| **Phase 3：评估迭代（持续）** | 评测流水线固化、回归集扩充、灰度观察、依据反馈调提示词/打分权重 | 达到 9.3 出口条件，冻结 MVP 并规划下一阶段 |

> 各阶段共用"一次调查必须有审计、必须可失败降级、必须成本受控"三条底线，从 Phase 1 起强制执行。

## 11. 风险与开放问题

| 风险 | 影响 | 应对策略 |
|---|---|---|
| **拿不到变更/发布事件** | 无法用"上线导致故障"缩小范围 | 不把变更作为主信号；用链路重建 + 指标基线对比 + 跨信号一致性弥补；报告明确"未含变更证据"；预留后续可选接入点 |
| **只有 traceId、无完整链路存储** | 重建依赖日志埋点，埋点不全时调用关系模糊 | 重建置信度标签（strong/weak）如实呈现；推 RPC 埋点补齐作为配套项目；弱重建时引导人工介入 |
| **DeepSeek 不支持 Structured Output** | 结构化产出不稳 | 统一 `ask_json` shim：提示词强约束 + jsonschema 校验 + ≤3 次重试 + 确定性兜底；结构化步骤用 `deepseek-chat` + temperature=0 |
| **日志量大、token 成本失控** | 成本高、响应慢、上下文爆炸 | 确定性预过滤 + 模板聚类（-85% token）；单事件 token/查询/时间三重预算；LLM 只读摘要不读原文大海 |
| **LLM 幻觉** | 错误根因误导值班 | 幻觉四件套：schema 校验、强制证据引用、确定性校验层、HITL + 失败回退；置信度分档 |
| **告警风暴/重复触发** | 打爆数据源与 LLM | 事件归一化去重、并发上限 + 排队 + 优先级 |
| **行业 SOTA 仅 ~42% Top-1** | 期望管理问题 | 产品定位写死"草稿 + 人复核"；承诺 Top-3 而非确诊；评审时对齐预期 |
| **评测集标注成本** | 回归集建设慢 | 优先复用历史复盘文档自动提取 + 人工抽检 30~50 条起步，随迭代扩充 |
| **开放问题 1** | — | 线上日志系统查询方言确认为 ES DSL / LogQL / KQL？ |
| **开放问题 2** | — | 业务 RPC 埋点是否已含 `rpc_direction`/`rpc_target`？ |
| **开放问题 3** | — | 告警平台 webhook 协议字段是否齐备？ |
| **开放问题 4** | — | 30~50 条历史故障标注集来源与脱敏流程？ |
| **开放问题 5** | — | DeepSeek 调用配额、并发上限与成本预算归属？ |

## 12. 权限与安全

### 12.1 只读优先
- Agent 全部工具对数据源只读；**本期不存在任何写操作工具**。未来加写工具也必须 `requires_human_confirm=True` + 独立权限门。

### 12.2 访问控制
- 三级角色：值班（查看/手动触发）、SRE（采信/纠偏/驳回、调参建议）、管理员（配置、数据源连接、审计查询）。
- 数据源连接凭证仅服务端持有，LLM 不接触任何凭证；查询走白名单索引/指标名校验，防止非法查询放大为数据面风险。

### 12.3 HITL 门控
- 报告对外生效需人工确认（MVP 默认"报告即草稿"，人工采信后才作为结论沉淀）。
- 任何"覆盖/修改既有结论"的 LLM 输出必须先过校验层 + 人工反馈入口。

### 12.4 审计留痕
- 全链路审计（RCA-060/061）：事件、每步工具调用与查询（可还原）、LLM 输入输出摘要、人工操作均落库不可变，保留 ≥ 90 天。
- 敏感数据（日志正文、trace 内容）在审计与报告中做必要脱敏展示。
