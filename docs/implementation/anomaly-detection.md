# 指标异常检测器实现细节

> 模块：`app/pipeline/anomaly_detection.py`
> 关联 PRD：§5.2（指标接入，确定性优先）
> 状态：Phase 0 已落地

## 解决什么问题

在 7 步工作流的**指标验证**步骤，把一段指标时序**确定性地**判断出"是否异常 / 什么形态 / 何时开始 / 多大幅度"，输出结构化摘要喂给 LLM，而不是把原始时间序列丢给模型。

**为什么要确定性**（PRD §5.2）：
- LLM 对纯数字的理解不可靠（会"看图说话"），且读 60~几百个点费 token；
- 报告要过确定性校验层（时间先验、跨信号一致性），需要**机器可核对的时间点**，不能是模型的模糊描述；
- 机器指标常是"排除项"（CPU/内存正常 → 不是机器问题），"排除"必须确定性地做。

## 核心方法

**组合三种确定性检测**，覆盖不同异常形态：

| 方法 | 抓什么 | 原理 |
|---|---|---|
| Z-score / 3σ | 突增 / 突降 | 检测窗口均值相对基线均值的标准偏离 ≥ z_threshold（默认 3） |
| MAD（中位数绝对偏差） | 持续走高/走低（渐变） | 比 σ 抗离群点，抓 3σ 抓不到的缓慢抬升 |
| 标准差对比 | 锯齿 / 抖动 | 检测窗口方差 > 基线 3 倍 |

**区分"突变(spike)"与"渐变(rise)"**（关键设计决策）：
- 看检测窗口**第一个点**是否已偏离基线（突变 = 起点就跳变）与**整体均值**偏离（渐变 = 整体爬升）的对比；
- 起点即偏离 → SPIKE；起点正常、整体爬升 → RISE/FALL。
- 这是最初实现的坑：只有 z_mean 判定时，渐变到一定程度 z 必超，RISE 分支永远不可达，全被归成 SPIKE。

**防微扰门槛**：`min_ratio`（默认 1.2）——检测窗口均值 / 基线均值 偏离 <20% 一律视为正常，防止基线的小幅抖动误报。

## 输出契约

`MetricAnomaly` dataclass：

| 字段 | 含义 |
|---|---|
| `metric` | 指标名 |
| `shape` | AnomalyShape 枚举：spike_up / spike_down / rise / fall / jitter / normal |
| `baseline_mean` | 基线窗口均值 |
| `anomaly_start` | 异常起始时间（检测窗口内第一个偏离点） |
| `current_mean` | 异常后窗口均值 |
| `ratio` | current / baseline（>1 增，<1 减） |
| `is_anomaly` | 是否异常 |
| `to_summary()` | 一行结构化摘要（供 LLM 精读 / 写入 Evidence.summary） |

`detect_anomalies()` 批量检测，按 `abs(ratio)` 降序返回异常列表。

## 已知边界与局限

- 需要至少一个"基线窗口"（默认前 50% 数据）；少于 `min_points`（8）无法判定。
- 基线完全平稳（std=0）时，任何达到 `min_ratio` 的偏离都判为突变。
- 阈值（z=3、mad=4、min_ratio=1.2）是经验默认值，真实数据需回归调参。
- 未做周期性/季节性处理（如业务日切、整点峰值会被误判）——Phase 2 可引入 EWMA / 时序分解。
