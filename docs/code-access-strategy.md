# 代码 / 业务文档接入策略（决策记录）

> 状态：已定论（2026-08-03）
> 背景：讨论"根因定位 Agent 是否应该看业务文档和 code，以及怎么检索"后的结论。
> 关联：`docs/PRD.md` §2.2（非目标）、Phase 3+ 拓展方向。

## 核心结论

**代码和业务文档该看，但角色是"诊断增强器"，不是"定位触发器"。**

- **定位（Localization）**：哪个服务/组件/代码路径出问题 → 遥测信号（日志/指标/链路/异常堆栈）就够，不需要代码/文档。
- **诊断（Diagnosis）**：为什么是它出问题 / 是不是代码 bug / 怎么修 → 代码/文档帮助巨大。

我们的架构定位是"定位为主，诊断给证据"。MVP 不系统接代码/文档；代码接入是 Phase 3+ 的事。

## 关键实证

- **MSACausalBench**：微服务 RCA 问答上，"原始源码作检索上下文"准确率 **0.93**，远超"自然语言文档"的 **0.59**。
  → 代码本身比"代码的文档"值钱；语义检索想解决的"理解意图"恰恰是文档最差、代码反而不差的场景。
- **字节 ErrorPrism（ASE 2025）**：静态分析（函数调用图）+ LLM 反向搜索，67 个生产微服务、98.8 万行 Go，错误传播路径重建准确率 **97%**。
- **Datadog Bits AI SRE**：跨 logs/metrics/traces/deploys/**code** 自主调查——代码是证据源之一。

## 检索策略：锚点决定工具（不是 grep vs 语义二选一）

| 方式 | 是什么 | 何时用 | 成本/风险 |
|---|---|---|---|
| **① 词法精确检索（grep/ctags）** | 按符号名、异常类、行号精确匹配 | **手里有锚点**（堆栈行号、错误串、类名）——80% 场景 | 低/零幻觉 |
| **② 结构化代码导航（静态调用图）** | 谁调用谁、方法依赖 | 需要**传播路径**时（checkout 超时 → 反查上游谁发起） | 中/结构化 |
| **③ 语义向量检索（embedding）** | 按"意思"检索代码块/文档 | **完全无锚点**的概念级探索 | 高/有幻觉风险 |

**决策规则**：
```
有明确锚点（符号/行号/异常串/服务名）──► ① grep + 读文件（确定性，永远优先）
需要传播路径 ────────────────────────► ② 静态调用图
无锚点、只有模糊问题 ───────────────► ③ 语义检索，但结果降级为"假设"，
                                           必须再过证据校验，不能当事实
```

**代码检索的推荐顺序**：先做 ①（最便宜最准），②③ 排后。
**业务文档**：最弱、甚至可能不做（实证代码 0.93 vs 文档 0.59）。真要接，只接每个服务的顶层摘要（"这服务管什么、有什么已知坑"），作为服务名已知时的快速上下文，不建大规模文档向量库。

## 对代码问题的处理边界

- 我们的"根因"定位到**服务/组件/代码路径**为止（靠异常堆栈精确到 `OrderService.java:123` 这类粒度）。
- 不自动改代码、不自动确诊；修复交研发。
- **异常堆栈 = 免费的代码指针**：MVP 阶段对"代码问题"的实际能力就是"靠堆栈把 Agent 和人一起带到具体文件行"。

## 落地路线

| 阶段 | 做什么 |
|---|---|
| MVP（Phase 0-1） | 不系统接代码/文档；**充分用好异常堆栈**（自带代码指针） |
| Phase 2（RAG） | 先接**知识库**（历史故障/runbook/已知问题）——比业务文档性价比高得多 |
| Phase 3+ | 按需接**代码检索**：已定位到具体接口/类时，用 ① grep（可加 ② 调用图）检索对应代码片段 |

> 风险提醒：脏文档比没文档更危险（调研原话）。知识库/代码索引都要治理。
