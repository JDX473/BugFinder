## 架构设计决策

### D1. 自研 agent 框架,不用 LangChain/AutoGen

**决策**:Agent 循环、工具注册、消息管理全部手写(~2000 行)。
**原因**:论文的 OBSK、JsonRegen、TSC 重放都需要对 prompt 逐 token 级控制
(净化、快照、重放重建消息),通用框架的抽象层会掣肘;
且手写让每条消息的组成完全透明,利于复现与排错。

### D2. 单一 JSON 交换格式 + 统一修复层

**决策**:controller 动作、expert 返回、聚合中间产物全部是 JSON,统一过 JsonRegen。
**原因**(论文 §III-C1):弱模型在复杂内容下结构化输出不可靠,JSONFormer/TypeChat
不适用(无法处理大量转义字符;只依赖 token 级纠错)。论文明确:即使 ChatGPT
在内容复杂时也会产生错误结构——所以 API 模型阶段修复层仍然必要。

### D3. 观察分层: head + snapshot,完整内容按需消费

**决策**:工具返回的长内容只展示 head,完整内容存快照库;controller 需要处理
完整内容时以快照键为参数调专家工具(由运行时解析)。
**原因**(论文 §III-A):上下文预算有限,且"提示信息存在"与"完整内容"解耦后,
专家工具可以按需消费完整数据,controller 的 prompt 保持受控长度。

### D4. 工具"语义极简"

**决策**:信息收集工具只接收简单参数(如 job_id),不暴露 SQL/查询 API。
**原因**(论文 §III-B1):降低 LLM 产生有效动作的难度,防止在数据仓库里无意义探索;
工具文档也因此更短,节省上下文。

### D5. 解码默认 greedy + 自适应惩罚

**决策**:默认 greedy(可复现);生成超过 4096 token 时重启并 +0.5 惩罚,可迭代。
**原因**(论文 §IV-A):抑制重复退化;论文实测采样解码(无示范历史)会让
Pass Rate 从 99% 崩到 70%——所以默认路径必须稳定。

### D6. TSC 而非全轨迹采样

**决策**:只在进入 finalize 时从倒数第二步开始采样 K 条子轨迹。
**原因**(论文 §III-D2):全轨迹采样成本高(expert 激活昂贵,API 模式成本直接翻倍);
且从第一步随机采样缺少历史示范会错误动作泛滥。greedy 主轨迹的稳定历史
充当 few-shot 示范。

### D7. 工具/数据源/代码仓库插件化

**决策**:Environment 协议(数据源)+ ToolRegistry(工具)+ repo_dir(代码仓库)
全部可插拔;适配新服务只动三处"服务专属件"(工具集、领域知识 prompt、知识库)。
**原因**:论文定位即"extendable to different cloud systems";也是目标服务
迟迟未定但开发不阻塞的关键。

### D8. 变体系统(variant)而非复制代码

**决策**:消融(react/no_experts/no_jsonregen/no_obsk/no_obs_head)通过
`RCAgent.build(variant=...)` 单点开关实现,不复制代码。
**原因**:保证消融对比时唯一变量是"被移除的机制",避免两份代码漂移。

## 工程决策

| 决策 | 原因 |
| --- | --- |
| 轨迹 JSONL 落盘,含每步确切 prompt | 复现排错;TSC 重放依赖 records 精确重建消息 |
| log_agent 结果缓存(按日志内容 hash) | 同一日志重复分析浪费 API 调用 |
| log_agent 分块并发(4 路) | chunk 间无依赖;真实评估从 30+ 分钟降到 ~15 分钟 |
| 分块按"可疑度"排序截断 | 错误块必进分析,纯正常区域在超限时被裁 |
| embedding 批次 20 | qwen API 上限;3000 行日志自动分批 |
| 测试统一 mock embedding | 框架逻辑测试确定性;真实 embedding 走端到端验证 |

## 复现优先原则

1. **论文优先**:所有参数以论文为准(窗口 200、K=10、0.9/0.6、15 步等),工程优化不得改变语义;
2. **诚实偏差**:与论文不一致处(模型、数据)显式记录,不粉饰;
3. **相对结论为目标**:数据集不同,数值不可比,目标是复现"RCAgent > ReAct 且消融梯度存在"的相对结论。
