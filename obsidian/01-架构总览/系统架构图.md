# 系统架构图

> 相关: [[与论文的对应关系]] | [[关键设计决策]] | [[Controller-Agent-循环]]

## 一句话架构

**一个 controller LLM 在"思考-行动-观察"循环中自主调用一组工具(含两个 LLM 专家),所有结构化输出经过 JsonRegen 修复,长观察经过 OBSK 压缩,错误行为被检测并反馈,最终以 finalize 工具输出四项 RCA 结果;多条轨迹可经 TSC 聚合成更稳健的答案。**

```mermaid
flowchart TB

    end
    Controller -->|"Thought + Function JSON"| R["Agent Runtime<br/>(rcagent/core/agent.py)"]
    R -->|"解析失败"| J["JsonRegen<br/>结构化修复层"]
    R -->|"工具校验/错误检测"| E["错误处理<br/>三类预定义错误"]
    R -->|"执行"| T["工具注册表 ToolRegistry"]
    T --> G["信息收集工具<br/>(服务专属件)"]
    T --> L["日志专家 log_agent<br/>(Algorithm 1)"]
    T --> C["代码专家 code_agent<br/>(递归读代码)"]

```


## 整体决策循环(loop 架构图)

**一张图看全**:任务进入 → LLM 生成 → 解析修复 → 校验 → 执行 → 观察回到记忆,
循环往复直至 finalize;所有失败路径都以"反馈"形式回到记忆(不终止循环)。

```mermaid
flowchart TB
    START["异常任务<br/>job_id / anomaly / detect_time"] --> MEM

    subgraph MEM["Controller Memory<br/>(system prompt 三件套 + 完整历史消息)"]
        GEN["LLM 生成<br/>Thought + Function JSON"]
    end

    GEN --> J["JsonRegen 解析<br/>(Algorithm 2)"]
    J -->|解析失败| ERR1["错误反馈:<br/>输出非法 JSON,请重试"]

    J --> CHK{"工具校验<br/>+ 错误检测<br/>(§III-C2)"}
    CHK -->|工具不存在/参数错误| ERR2["错误反馈:<br/>工具/参数问题"]
    CHK -->|重复调用/trivial/过早finalize| ERR3["错误反馈:<br/>+ 改进建议"]
    CHK -->|通过| EXE["执行工具<br/>(快照键先经 OBSK 解析)"]

    EXE -->|"信息收集工具<br/>runtime/platform/infra log"| OBS["观察:<br/>head + [snapshot: key]"]
    EXE -->|"专家工具<br/>log_agent / code_agent"| EXP["专家分析<br/>(Algorithm 1 / 图4)"]
    EXP --> OBS

    subgraph KV["OBSK 键值库<br/>(snapshot key → 完整内容)"]
        SNAP["完整观察内容"]
    end
    EXE -.存入.-> SNAP
    OBS -->|"观察(head)注入消息历史"| GEN

    ERR1 --> MEM
    ERR2 --> MEM
    ERR3 --> MEM

    EXE -->|finalize| FIN{"四项结果校验<br/>root_cause/solution/evidence/responsibility"}
    FIN -->|缺字段| ERR4["错误反馈:<br/>字段缺失"] --> MEM
    FIN -->|通过| OUT["RCA 结果"]
    OUT --> TSC["TSC 聚合(可选)<br/>从倒数第二步重放 K 条子轨迹<br/>→ LLM 聚合 / embedding 投票"]
```

**循环的四个回路**(图中全部回到 Memory):

| 回路 | 触发 | 意义 |
| --- | --- | --- |
| 正常回路 | 工具执行成功 | 观察推进调查(head + 快照键) |
| 解析回路 | JsonRegen 修复失败 | 提示重新输出合法 JSON |
| 校验回路 | 工具/参数/三类错误 | 提示修正动作(不终止) |
| 出口回路 | finalize 四项齐全 | 输出结果,循环结束 |

**与论文图2 的对应**:左半(Thought and Action → Parsed Action → Environment → Observation → Memory)即上图主回路;论文右侧的 key-value store(OBSK)、expert agent(专家工具)、error handling(三条错误回路)全部落在对应的子图上。

## 一次典型运行的完整数据流

以 `demo_es_conn_timeout` 为例(真实模型运行,10 步):

```
1. 构造 JobDesc(job_id, anomaly, detect_time)
2. Agent Runtime 组装 system prompt(三件套) + user prompt(作业描述)
3. 循环(最多 15 步):
   a. LLM 生成 "Thought + Function JSON"
   b. JsonRegen 修复 → 解析出 {function, kwargs}
   c. 校验: 工具存在?参数合法?错误检测(重复调用/trivial/过早finalize)?
   d. 执行工具(参数中的快照键先经 OBSK 解析为完整内容)
   e. 返回观察 head(+快照键)注入消息历史
   f. 若调用 finalize → 校验四项 → 退出
4. 结果 {root_cause, solution, evidence, responsibility}
5. (可选) TSC: 从倒数第二步重放 K 条采样子轨迹 → LLM 聚合
```

## 关键设计点

1. **单一数据交换格式**:controller 的动作、expert 的返回、聚合的中间产物全部是 JSON,经 JsonRegen 统一修复(论文: "JSON is chosen as the data interchange format")。
2. **无 few-shot**:与原始 ReAct 不同,RCAgent 丢弃 few-shot 示例(上下文预算),greedy 解码的轨迹历史本身充当示范(论文: trajectory-level zero-shot)。
3. **专家即工具**:log_agent/code_agent 对 controller 而言只是两个工具,但内部是独立的 LLM 推理流程——分析工作从 controller 的上下文里被"外包"出去。
4. **观察分层**:controller 只看到 head(或快照键),完整内容按需由专家消费——这是论文处理超长上下文的核心手段。
5. **一切可复现**:每条轨迹 JSONL 落盘(含每步送入 LLM 的确切 prompt),TSC 可从主轨迹 records 精确重建消息历史。
